## ドメインの変換はHandlerとUseCaseのどちらでやるべきか

- Source: https://zenn.dev/jisou/articles/b7e19c4a2d80f6
- Author: Watanabe Jin
- Published: 2026-09-21
- Tags: TypeScript, design, DDD, clean-architecture
- Reliability: **78/100**

### Summary

APIのRequestからDomain Objectを生成する場所を、HandlerとUseCaseのどちらに置くべきか比較した設計記事。

Handlerで `new User(...)` すればUseCaseは最初からDomain Objectを受け取れるため、UseCaseを処理手順に集中させやすい。一方でHandlerがDomain Objectを直接保持すると、表示都合など外側のロジックをDomainへ追加しやすくなり、外部境界とDomainの結合が強くなるという問題を指摘する。

著者は、型が使えるDomain中心のアプリケーションでは、HandlerはRequestをUseCase専用のParamsへ変換するところまでに留め、UseCaseを起点にDomain Objectを生成する構成を基本案としている。

```text
External Request
      ↓
   Handler
      ↓
UseCase Params
      ↓
   UseCase
      ↓
Domain Object
```

失敗も3種類に分けている。

- JSON破損・必須キー不足・型不正など「形式の失敗」: Handler
- 空の名前・不正なメールなど「Domainの不変条件」: Domain
- メール重複・会社枠超過など「業務上この操作を許可できない失敗」: UseCase

複数のREST/Batch/CLIなどから同じUseCaseを呼ぶ場合にも、Domain生成と業務上の検証を内側へ集約できる。

### Author's conclusion

「常にUseCaseが正解」とはしていない。型がない場合や、明確なDomainをほとんど持たないHub APIなどではHandler側で変換する実装も現実的としている。

### Reliability view

この記事は「HandlerかUseCaseか」という唯一の正解が存在する仕様解説ではなく、依存方向と責務分割についての設計上の主張。コード例と反対案を示し、前提条件も明示しているため議論としての透明性は高い。

一方、「HandlerがDomainを持つと外側のロジックがDomainへ入りやすい」「UseCase起点ならそのミスが減る」といった部分は設計経験に基づく見解であり、Clean ArchitectureやDDDから一意に導かれる規則ではない。

### Agent view

将来この知識を使う場合は「UseCaseでnewするのが正解」というルールとしてではなく、**外部Requestの構造・UseCaseの入力契約・Domain生成の責務をどこで分離するかを考える設計パターン**として扱う。

## Node.js 26.9.0公開、Web Workers対応やnode:benchを追加

- Source: https://codezine.jp/news/detail/29759
- Author: CodeZine編集部
- Published: 2026-09-22
- Tags: Node.js, JavaScript, release, Web-Workers, benchmark
- Reliability: **97/100**

### Summary

Node.js 26.9.0が2026年9月16日にリリース。

主な変更:

- workerモジュールでWeb Workersをサポート
- ベンチマーク用の `node:bench` を実装
- `node:ffi` をデフォルトで有効化
- VFSをCJS/ESMモジュールローダーへ統合

### Reliability view

リリース内容を伝える短いニュースで、主要項目はNode.js公式v26.9.0リリース情報と一致する。独自の性能評価や推測をほぼ含まないため高信頼。

### Practical implications

Node.js自体にWeb標準との互換性を高める機能やベンチマーク基盤が増えている。特に `node:bench` は将来的にNode.js標準だけで性能計測を組み立てられる可能性があるが、現時点ではexperimental扱いに注意する。

## React Router の新しい useRouterState で Pending UI を考える

- Source: https://zenn.dev/astrologian/articles/562fe3f749d985
- Author: Relu
- Published: 2026-09-22
- Tags: React, TypeScript, frontend, UX, React-Router
- Reliability: **91/100**

### Summary

React Router v7.15.1で追加された実験的Hook `unstable_useRouterState` を使い、画面遷移完了前の情報からPending UIを作る方法を解説。

`useRouterState()` は現在のRoute情報を `active`、遷移先を `pending` として扱う。既存Hookの情報を統合するだけでなく、従来直接取得できなかった遷移先の以下を参照できる。

- `pending.params`: 遷移先Route parameter
- `pending.matches`: 遷移先でmatchするRoute階層
- `pending.type`: PUSH / REPLACE / POP

記事ではData Modeを前提に、`pending.params` で遷移先IDを先読みして選択状態や既知データを即時表示する例、`active.matches` と `pending.matches` の最初の差分から「どのOutlet以下が入れ替わるか」を判定してスケルトン範囲を限定する例を示す。

さらにRouteの `handle` をpending matchesから読み、遷移確定前にタイトル、breadcrumb、content width、skeleton typeなどを決めるアイデアを提示する。

`pending.type` は履歴操作だけを表すため、POPだけではback/forward方向は判別できない。記事ではparamsのstep差分と組み合わせ、forward/back/restartのアニメーションを切り替える例を示している。

### Important caveat

`useRouterState` は現在も `unstable_` prefix付きの実験的APIで、minor/patch releaseでもbreaking changeの可能性がある。記事自身もこの点を明記している。

Framework Modeなどで遷移先Route moduleが未ロードの場合、pending matchの `handle` が未取得になる場合があり、記事では `prefetch="intent"` による先読みも紹介している。

### Reliability view

React Router公式ドキュメントとv7.15.1 changelogで、useRouterStateの追加、active/pending構造、pending params/matches/type、experimentalである点を確認できる。中核となる技術説明は一次情報と一致する。

Pending UIの具体的な設計は著者による応用例なので、公式推奨パターンそのものとは区別する。

### Practical implications

遷移開始からloader完了までを単なるspinnerで埋めるのではなく、「次にどこへ行くか」が既に分かっていることを利用して、optimisticに近いPending UIを構築できる。

## Delta LakeとIcebergの違いを、いつものSQLから考える

- Source: https://zenn.dev/cybernetics/articles/f3d60a4e325a17
- Author: HELLO_CYBERNETICS
- Published: 2026-09-22
- Tags: Databricks, Delta-Lake, Apache-Iceberg, Lakehouse, Open-Table-Format
- Reliability: **94/100**

### Summary

Parquetだけでは「現在どのファイル群がテーブルを構成するのか」「更新をどこで確定するか」「削除済みの行はどれか」などを管理できない。Delta LakeとApache Icebergは、その上にテーブルとしての状態・メタデータ・トランザクションを持たせるOpen Table Formatとして説明される。

両者をSQL利用者の視点から比較する。

#### Multi-engine

Icebergはエンジン非依存のmetadataとCatalogを通じ、Spark/Trinoなど複数エンジンで同じテーブルを共有しやすい。REST Catalogという共通APIもある。

Deltaも公開仕様を持ち複数エンジンから利用できるが、各エンジンでread/writeなど対応範囲が異なる。UniFormではDeltaのParquetにIceberg metadataを生成してIceberg対応エンジンから読む構成も可能。

#### ファイル探索

Iceberg:
```text
Snapshot
  ↓
Manifest List
  ↓
Manifest
  ↓
Data Files
```

manifestのpartition/statisticsなどを使って候補を段階的に絞る。

Deltaは `_delta_log` にadd/removeなど変更履歴を記録し、checkpointとそれ以降のlogから現在のtable stateを構築する。ファイル統計を利用したdata skippingも行う。

この違いだけから「Icebergの方が速い」とは言えず、ファイル配置・metadata量・engine実装・cacheなども性能へ影響する。

#### Data layout evolution

IcebergはHidden Partitioning / Partition Transform / Partition Evolutionにより、利用者のSQLから物理partition設計を切り離しやすい。

DeltaのLiquid Clusteringは固定partitionへの依存を減らし、後からclustering columnsを変更できる。

#### DELETE

Parquetファイルの一行だけを物理的にその場で書き換える代わりに、削除情報を別管理できる。

Delta: Deletion Vector。

Iceberg: v2のPosition/Equality Delete、v3のDeletion Vector。したがって「DeltaにはDVがありIcebergにはない」という比較は現在は誤り。

ただしsoft delete的な管理ではread時の処理や後続compaction/purgeなど別のコストが発生する。

#### Compatibility

「Open Format = どのengineでも全機能が使える」ではない。

Deltaにはprotocol/table features、Icebergにはformat versionがあり、新機能を有効化すると未対応reader/writerから扱えなくなる可能性がある。導入時は「Iceberg/Delta対応」という表記だけでなく、format versionとfeature単位で確認する必要がある。

### Reliability view

記事は公式資料を多数参照し、主要説明もApache Iceberg仕様、REST Catalog仕様、Delta Lake公式ドキュメントと整合する。

特にIceberg v3でDeletion Vectorが追加されたこと、Delta DVがParquet rewriteを回避する仕組み、Liquid Clusteringでclustering columnsを変更できることは一次資料で確認できる。

また著者自身が「Icebergの方が速いとは言えない」「engineごとの対応範囲を確認する」と断定を避けており、比較記事として慎重。

### Practical implications

Delta vs Icebergを機能一覧だけで選ばず、

1. どのengineからread/writeするか
2. 必要なformat/table featureを各engineが実装しているか
3. metadata/file planningの特性
4. update/delete頻度
5. data layoutを将来変更する可能性

で判断する方が実運用に近い。
