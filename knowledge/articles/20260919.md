## AIに丸投げしないで理解するためのAI開発手法（2026年8月現在）

source: https://zenn.dev/avaintelligence/articles/dont-outsource-understanding-to-ai

tags: [ai, coding-agent, understanding, engineering]

### 要約

AIコーディングツールを活用しながらも、人間がシステムへの理解を失わないための開発手法についての記事。

AIに実装を丸投げすると、従来からある「技術負債」に加えて「理解負債」が蓄積する。AIは人間よりはるかに速い速度で大量のコードを生成できるため、人間が内容を理解しないまま「動いたからOK」と進めると、コードベースについて説明・判断できない領域が急速に増える。

そこで著者は、AIを使わないのではなく、AIによって作られるものを人間が理解できるプロセスを開発フローに組み込んでいる。

大まかな流れは、GitHub Issueなどでビジネス要件を整理し、AIにコードをいきなり書かせるのではなく、まず詳細な実装計画を作らせる。その計画を人間がレビューし、要件を満たしているか、重要なビジネスロジックがテスト可能になっているか、必要なテストケースが考慮されているかなどを確認する。

ただしAIが作る計画自体が数千行になることもあり、それを人間がそのまま読むことも現実的ではない。そのため著者は `explain-visually` のようなSkillを作り、巨大な実装計画を人間が理解しやすい形へ再構成してからレビューしている。

重要なのは「AIに仕事をさせない」ことではなく、人間が重要な設計判断やビジネスロジックを理解した状態を維持すること。

AI時代にはコードを書く速度より、「AIが作ったものについて人間が説明・判断できる状態をどう維持するか」が重要になる。

### 要点

- AIによって技術負債だけでなく「理解負債」が高速に蓄積する。
- コード生成前にAIに詳細な実装計画を作らせる。
- 人間は計画段階で要件・設計・テスト可能性をレビューする。
- AIが作った巨大な計画も別のAI/Skillで人間が理解できる形へ変換する。
- AIへの委譲と、人間が理解を放棄することは別問題。
- AI時代には「理解するための工程」そのものを開発プロセスとして設計する必要がある。

## skilldoctor

source: https://github.com/xyiqq/skilldoctor

tags: [ai, agent-skills, quality, tooling]

### 要約

Agent Skillの品質を検査するためのツール。

AIエージェント用SkillはMarkdown中心で簡単に作れる一方、外部から取得したSkillをそのまま信用すると、品質・安全性・互換性などに問題がある可能性がある。

skilldoctorはSkillを静的に検査し、構造上の問題、危険なinstruction、各種AIコーディングエージェントとの互換性などを確認するための品質ゲートとして利用できる。

Skillを「ただのプロンプトファイル」ではなく、ソフトウェアのようにlint・検証するという発想が重要。

Yggdrasil自身を将来的にAgent Skill化した場合にも、Skillを人間の感覚だけで更新するのではなく、機械的に検証する考え方が利用できる。

### 要点

- Agent Skillにもlintや品質検査が必要。
- 外部Skillを無条件で信用しない。
- instructionの安全性も検査対象になる。
- Claude/Cursor/Codex/OpenCode/Gemini CLI/GitHub Copilotなど複数環境との互換性を意識する。
- Skillをコードと同じようにテスト可能な成果物として扱う。

## 設計書・コード・テストを全部AIに書かせて半年間開発してみた

source: https://zenn.dev/nttdata_tech/articles/8a010aff542625

tags: [ai, software-development, github-copilot, case-study]

### 要約

NTT DATAの実案件において、設計書、ソースコード、テストケースなどの開発成果物をすべてGitHub Copilotに生成させ、人間はレビューに徹する開発を半年間実践した記録。

対象はAWS上で動作する商用システムのサブシステムで、スクラッチ開発。社員3名で開発し、開発経験の豊富な社員がメンターとして参加した。

特徴的なのは、社員が設計書・コード・テストケースを基本的に手書きせず、AIが成果物を作り、人間がレビューする役割分担を実際の商用開発で試したこと。

AIに安定して作業させるには単純なプロンプトだけでは足りず、ドキュメントフォーマット、各種プロンプト、開発ルール、ディレクトリ構造、タスクフォーマット、Copilotへの共通指示など、AIが仕事をするための環境整備が必要になる。

設計・製造では大きな効果が得られる一方、テストケースの抽出不足などAI生成物の品質問題は残る。また、バグ情報などをMarkdown中心で管理すると、後から定量分析しにくいといった問題も発生した。

「AIが書けるか」だけではなく、「AIが生成した大量の成果物をどのようにレビュー・検証・分析するか」まで設計する必要がある。

### 要点

- 商用システムで半年間AIネイティブ開発を実践。
- 設計書・コード・テストケースをGitHub Copilotが生成。
- 人間の主な仕事はレビュー。
- AIの能力だけではなく、ルール・フォーマット・タスク構造などの環境整備が重要。
- AI生成量が増えると、人間のレビュー能力がボトルネックになりうる。
- MarkdownはAIには扱いやすいが、定量分析用途では構造化データが必要になる場合がある。

## ハーネスエンジニアリングを極めたら、人間の役割は要件定義だけになった

source: https://zenn.dev/aicon_kato/articles/harness-engineering-startup

tags: [ai, harness-engineering, agent, software-development]

### 要約

スタートアップで、AIエージェントが要求から実装・レビュー・PR作成まで進められる自律開発パイプラインを構築した事例。

約57万行のプロダクトコードに対し、21体のAIエージェントからなる開発パイプラインを約2か月で構築した。

重要なのは「高性能なモデルを使う」ことだけではなく、AIが自律的に仕事を完了できる環境を作ること。

GitHub Issueを仕事の起点とし、要求をタスクへ分解し、各エージェントがラベルなどを使って次工程へ仕事を受け渡す。CI/CD、PRごとのプレビュー環境、テスト、レビュー、コードベースの品質評価なども自動化する。

開発期間の一部では機能開発を止めてCI/CDやハーネスの整備そのものへ投資している。短期的には機能開発速度が落ちても、その後AIが自律的に開発できる環境を作ることでスループットを上げる考え方。

ハーネスエンジニアリングとは、モデルそのものを改善するのではなく、「モデルが失敗を検知し、修正し、仕事を完了できる外部環境」を設計することと捉えられる。

### 要点

- IssueをAIの仕事の中心に置く。
- 要求→設計→実装→レビュー→PRなどを工程化する。
- エージェント同士の受け渡しを機械的に管理する。
- CI/CD・テスト・プレビュー環境がAIのフィードバックループになる。
- AIの性能より、AIが試行錯誤できる環境設計が重要。
- 人間の仕事は実装から要件・制約・評価基準の設計へ移動していく。

## ハーネスエンジニアリングとは何か — 用語整理

source: https://zenn.dev/watany/articles/d8b692bbca65a3

tags: [ai, harness-engineering, terminology]

### 要約

「ハーネスエンジニアリング」という言葉が異なる意味で使われ始めている状況を整理する記事。

重要な区別として、AIエージェントそのものを作る側がモデルの周囲に構築するハーネスと、Claude Codeなど既存のエージェントを利用するユーザーが自分の開発環境に構築するハーネスがある。

後者では、AGENTS.md、Skills、MCP、テスト、lint、CI、ドキュメント、リポジトリ構造などが「AIが正しく働くための外部環境」となる。

この区別をしないと、モデル内部のエージェント設計の話と、開発者がリポジトリに何を用意するかという話が混ざる。

Yggdrasilを設計するときにも、モデル自体を制御しようと大量のプロンプトを書くより、必要な知識を検索できる構造、明確な保存規則、検証可能な出力など「利用者側のハーネス」を整える方が重要。

## Prompt → Context → Harness / Shogun Harness Engineering

source: https://zenn.dev/shio_shoppaize/articles/shogun-harness-engineering

tags: [ai, harness-engineering, context-engineering, workflow]

### 要約

AI開発の方法論を、Prompt Engineering → Context Engineering → Harness Engineeringという進化として捉える考え方。

Prompt Engineeringでは「AIにどう質問するか」が中心だった。

Context Engineeringでは、AIにどの情報・履歴・ドキュメント・ツールを渡すかが中心になる。

Harness Engineeringではさらに一歩進み、AIが仕事を繰り返し実行し、結果を検証し、失敗したら修正し、次工程へ進むためのワークフローそのものを設計する。

著者はハーネスを、従来GitHub上で人間・CI・レビュー工程が担っていた開発ワークフローを、AIエージェントが利用できる形へ再構成するものとして捉えている。

重要なのは「賢いAIを呼び出す」ことではなく、仕事を小さな工程に分け、それぞれに入力・出力・検証・失敗時の処理を定義すること。

## ユーザーハーネスについて

source: https://zenn.dev/r_kaga/articles/329afdc151899f

tags: [ai, harness-engineering, coding-agent]

### 要約

AIエージェントを利用する側が整備する「ユーザーハーネス」という考え方を扱う資料。

Claude Codeなどのモデル/エージェントそのものを変更しなくても、リポジトリ側にルール、ドキュメント、MCP、Skills、テスト、開発コマンドなどを整備することで、AIの仕事の品質を大きく改善できる。

Laravel Boostなどの仕組みも、このユーザーハーネスをフレームワーク側が提供する例として理解できる。アプリ状態・DB・ログ・ルートなどをAIが参照できるMCP、フレームワーク固有のGuidelines、必要時だけロードするSkills、現在利用しているバージョンに対応したDocumentation APIなどが該当する。

「AIを賢くする」のではなく、「AIが必要な情報と検証手段へアクセスできる環境を作る」という考え方。

## Prompt / Context / Harness と要件定義

source: https://zenn.dev/gvatech_blog/articles/30f79910d111bb

tags: [ai, requirements, context-engineering, harness-engineering]

### 要約

AIによる実装能力が向上するほど、人間の価値が「コードを書くこと」から「何を作るべきか、何を正しい状態とするかを定義すること」へ移っていくというテーマ。

プロンプトだけを工夫する段階から、必要なコンテキストを整備する段階、さらにAIが継続的に仕事を実行・検証できるハーネスを整える段階へと進む。

AIが実装を大量に生成できる状況では、曖昧な要件を高速に実装しても価値にはつながらない。むしろ誤った方向へ高速に進む危険がある。

そのため、Spec（何を満たすべきか）、Context（判断に必要な情報）、Harness（実行・検証の仕組み）を分離して設計することが重要になる。

## SKILL.md を良くする技術。AIのブレをなくす

source: https://zenn.dev/knowledgesense/articles/9adf1e9b17ffd6

tags: [ai, agent-skills, self-evolving-agent, harness]

### 要約

AIエージェントのSkillを継続的に改善するとき、「問題が起きたらAIに適当に直させる」という運用ではSkillそのものが不安定になり、昨日と今日で挙動が変わる問題が起きる。

記事ではIBM ResearchなどによるSelf-Evolving Agentsの研究を紹介し、Skill改善そのものを定型化されたハーネスとして設計する考え方を説明する。

重要なのは、発生したエラーだけを修正するのではなく、Skill全体を評価し、将来的に曖昧さやブレを生みそうな箇所まで検出して改善すること。

つまりAI自身にSkillを改善させる場合でも、

評価 → 問題検出 → 改善案 → 修正 → 再評価

というフィードバックループが必要。

YggdrasilのAGENTS.mdやSkillsも将来的にAI自身が改善する可能性があるが、自由編集させるのではなく、改善プロセスをハーネスとして定義する方が安全。

## Claude Codeで分析エージェントを作って3か月運用した話

source: https://note.com/guchey/n/n9eb66dd5d470

tags: [ai, data-analysis, claude-code, context-engineering]

### 要約

Claude Codeを利用し、プロダクト指標の変動原因を自律的に調査する分析エージェントを構築・運用した記録。

当初はText-to-SQL、つまり自然言語からSQLを書ければ分析を自動化できると考えた。しかし実運用では、SQL生成能力よりも「なぜその数字が変わったのか」を判断するための文脈が重要だった。

著者は分析エージェントに必要な情報を大きく3層に整理する。

1. データ層  
   テーブルや指標の意味を整理し、「何が起きているか」を正確に把握できる状態にする。

2. 分析層  
   セグメント分解、時系列比較、異常検知など、どのように原因を探索するかを定義する。

3. 文脈層  
   UI変更、施策、プロダクト変更、外部環境など、データそのものには存在しない情報を提供する。

文脈層がないとAIは、与えられたデータの中だけで無理に原因を説明し、「もっともらしい嘘」を作ることがある。

Claude Codeは、一つのSQL結果を見て次のSQLを考え、さらに別のデータを調べるという探索的分析と相性がよい。

一方、運用によって明らかな誤りを減らすことはできても完全にはなくならない。分析エージェントは分析能力のある人の生産性を大きく高めるが、分析リテラシーそのものを代替するものではない。

### 要点

- Text-to-SQLだけでは分析エージェントにならない。
- データ・分析方法・事業文脈の3層が必要。
- AIが見られる世界を限定すると、その範囲内で誤った説明を作る可能性がある。
- プロダクト変更や施策履歴などの「データ外の情報」が重要。
- 過去の失敗や訂正をナレッジとして残すことで改善できる。
- AIは専門家を置き換えるより、専門家の探索能力を増幅する。

## プロダクトエンジニアに必要な「いい感じ」に作る能力

source: https://zenn.dev/dress_code/articles/fc3d9e985a1a8c

tags: [product-engineering, product-management, decision-making]

### 要約

AIによって実装能力が大幅に向上し「作ろうと思えば大量に作れる」時代に、プロダクトエンジニアに必要になる判断力についての記事。

著者がいう「いい感じに作る」とは、仕様を忠実に全部実装することではない。

プロダクト、顧客、組織の現在の状況を見て、「今どこまで作るべきか」「逆に何を作らないべきか」を判断する能力を指す。

実例として、開発中に得られた情報から、当初企画されていた検索機能をあえて作らない判断を紹介する。

開発を進めることで、企画時には見えていなかった技術的制約、ユーザー行動、周辺機能との関係などが見える。その情報を企画へフィードバックせず「チケットに書いてあるから全部作る」とすると、不要な機能や手戻りが増える。

AIによって実装速度が上がっても、何を作るかの判断が高速化するとは限らない。むしろ実装コストが下がるほど「作れるから作る」という罠に陥りやすい。

### 要点

- 「作れる」と「作るべき」は別。
- 実装中に得た情報を企画へフィードバックする。
- 必要なら機能を「作らない」という判断をする。
- AIで実装速度が上がるほど、プロダクト判断の重要性が増す。
- プロダクト・顧客・組織を同時に見る。

## 現場で役立つ技術負債の効果的な返済方法

source: https://speakerdeck.com/masuda220/genba-de-yakudatsu-gijutsu-fusai-no-koukatekina-hensai-houhou

tags: [software-design, technical-debt, refactoring]

### 要約

技術的負債を抽象論ではなく、実際の開発現場でどう返済するかを扱った資料。

技術的負債によって、

- どこに何が書いてあるか理解するのが難しい
- 一つの変更のために複数箇所を修正する必要がある
- 小さな変更が予想外の場所へ影響する
- 修正のたびに大規模な手戻りが起きる

といった問題が発生する。

重要なのは、大規模な全面リライトを技術負債返済と考えないこと。限られた時間の中で、日々の変更と合わせて構造を少しずつ改善する。

既存コードだけでなくデータベース設計も重要な対象となる。コードを整理しても、データモデル自体が業務概念を正しく表現していなければ変更容易性は上がらない。

技術負債を「古い技術を使っていること」ではなく、「変更するためのコストが高い構造」として見る視点が重要。

## 技術に興味がなくて何が悪い？

source: https://qiita.com/indigonightism/items/c1bf747bed15e2840936

tags: [career, engineering, learning]

### 要約

「技術そのものに強い興味を持っていなければエンジニアに向いていない」という価値観に対する反論。

著者は技術への興味が強くないと自認しながら、エンジニアとして仕事を続けている。

重要な区別は「興味」と「行動」。

仕事や将来のキャリアに必要なら、興味がなくても勉強することはできる。これはエンジニアに限らず、多くの職業で普通に行われている。

一方で、技術が心から好きで常に考えている人と純粋な技術力だけで競争すれば、不利になる可能性はある。しかしエンジニアに必要な能力は純粋な技術力だけではない。

顧客とのコミュニケーション、チーム間の連携、リーダーシップ、マネジメントなど別の能力との組み合わせでも価値を出せる。

また、最初は興味がなくても、必要だから学習・実践を続けた結果、後から興味が生まれることもある。

### 要点

- 技術への興味とエンジニアとしての適性は同じではない。
- 興味と行動を分離して考える。
- 必要なら興味がなくても学習する。
- 技術力以外にもエンジニアとして価値を出す方法はある。
- 「好きでなければならない」という職業観に縛られない。

## Rethinking skills and prompts for GPT-6 Astra

source: https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra

tags: [ai, agents, prompting, skills, agents-md]

### 要約

高性能なコーディングモデルの登場によって、過去のモデル向けに蓄積した大量の指示が、逆にモデルの能力を阻害する可能性があるというOpenAIの記事。

これまでコーディングエージェントを安定させるため、AGENTS.md、Skills、タスクプロンプトなどへ大量の細かな指示を追加する運用が行われてきた。

しかしモデルの能力が向上すると、以前必要だった細かい手順説明や過剰なscaffoldingが不要になり、古い指示がモデルの判断を制約したり、コンテキストを圧迫したりする。

そのため、新しいモデルへ移行するときには「指示を追加する」のではなく、既存の指示を削除・整理することも重要。

Skillのdescriptionは、いつそのSkillを利用すべきかを判断できる程度に簡潔かつ限定的にする。

AGENTS.mdへすべての知識を書いたり、毎回大量の資料を読ませたりするのではなく、必要な情報を必要になった時点で取得するprogressive disclosureの設計が重要になる。

Yggdrasilにとって直接重要な知見であり、巨大なAGENTS.mdを作るのではなく、

- AGENTS.mdには基本的な行動原則だけを書く
- 詳細知識はknowledge配下へ置く
- 質問に応じて必要な資料だけ検索・取得する

という構造を支持する。

### 要点

- 高性能モデルには過剰な指示が逆効果になる場合がある。
- 古いモデル向けの指示を定期的に見直す。
- AGENTS.mdを巨大化させない。
- Skill descriptionは簡潔で利用条件が明確なものにする。
- 必要な情報だけ段階的にロードする。
- 「もっと指示を書く」より「不要な指示を消す」ことが重要になる。

## AIが大量に成果物を生成する時代のレビュー問題

source: https://qiita.com/take-yoda/items/e5d9ce6618523af1ffc5

tags: [ai, review, documentation, engineering]

### 要約

生成AIによってコードやドキュメントを大量かつ高速に生成できるようになった一方、人間がそれらを理解・レビューできる速度は同じようには向上しないという非対称性を扱う。

AI導入によって「作成」がボトルネックではなくなると、次のボトルネックは検証・レビュー・意思決定へ移動する。

大量のドキュメントを生成できること自体は価値ではなく、人間が必要な判断を行える情報量・構造になっている必要がある。

これは理解負債の問題ともつながる。

AIの生産速度に合わせて人間がすべてを読むことは不可能なので、生成物を減らす、構造化する、重要な差分だけ見せる、自動検証できるものを人間のレビュー対象から外す、といった設計が必要になる。

# 今日の資料を横断して見えるテーマ

今日集めた資料には、AI時代のソフトウェア開発について共通する考え方がある。

## 1. モデルの能力より「モデルの外側」が重要になる

高性能なAIを導入するだけでは安定した仕事はできない。

必要になるのは、

- 正しいコンテキスト
- ドキュメント
- 明確な要件
- Tools / MCP
- Skills
- テスト
- lint
- CI/CD
- プレビュー環境
- レビュー
- 失敗から学習する仕組み

など、モデルが仕事をするための環境である。

これがハーネスエンジニアリングの中心的な考え方。

## 2. AIが速くなるほど、人間の理解がボトルネックになる

AIはコード、設計書、テスト、ドキュメントを人間より圧倒的に速く生成できる。

しかし人間が理解・レビューできる速度は急には上がらない。

その結果、

生成速度 > 理解速度

となり、「理解負債」が蓄積する。

したがってAI時代の開発では、生成能力だけではなく、

「人間が何を理解すべきか」
「何を自動検証へ移すか」
「どの段階で人間が判断するか」

を設計する必要がある。

## 3. 人間の役割は実装から判断へ移動する

AIが実装を担える範囲が広がるほど、人間には、

- 何を作るか
- なぜ作るか
- 何を作らないか
- 何を正しい状態とするか
- どの制約を守るべきか
- 何をレビューすべきか

といった判断が重要になる。

「プロダクトエンジニアに必要な『いい感じ』に作る能力」と、
ハーネスエンジニアリングの記事は一見別テーマだが、
どちらも「実装そのものより上位の判断が重要になる」という点でつながっている。

## 4. コンテキストは単なる資料ではない

分析エージェントの記事では、SQL生成能力よりも、

- データの意味
- 分析方法
- プロダクト変更
- 過去の施策
- 外部環境
- 過去の失敗

などのコンテキストが重要だった。

これはYggdrasilにも直接当てはまる。

単に記事を保存するだけではなく、
「過去にどのような考え方・事例・失敗を知ったか」をAIが検索できる状態にすることが価値になる。

## 5. Yggdrasil自身も巨大なプロンプトにしない

OpenAIのSkills/Promptに関する知見から、
YggdrasilのAGENTS.mdへ全知識を書き込む設計は避ける。

AGENTS.mdは薄く保つ。

具体的な知識はMarkdownとして蓄積し、
質問が来たときにAIが検索して必要な資料だけ読む。

つまり、

質問
↓
関連知識を検索
↓
必要なMarkdownだけ読む
↓
複数資料を比較・統合
↓
回答
↓
参照した資料を提示

という構造にする。

これはYggdrasilの基本設計とする。
